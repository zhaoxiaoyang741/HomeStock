## Problem Statement

HomeStock 已有真实用户，但核心瓶颈正在显现：

- **输入摩擦太高**：用户购物回来要手动逐条录入物品，忘记 @ 机器人，希望用语音、图片、批量方式录入
- **渠道单一**：目前只有飞书 bot 作为交互出口，用户在其他平台（微信、Telegram）收不到通知
- **没有变现路径**：有用户无收入，需要找到第一个付费功能

与此同时，用户的真实行为模式表明：**他们不是在「使用」这个产品，而是在「伺候」它。** 任何需要用户主动操作的录入方式都会限制增长。长期方向应该是让录入自动发生（淘宝订单导入、小票拍照识别），但近期应该把现有录入的摩擦降到最低。

## Demand Evidence

- 有真实用户在主动使用 HomeStock
- 用户核心痛点是「忘记家里有什么，结果重复买」——这是具体的行为证据，不是假设
- 用户自发展示了多模态输入需求（语音、图片、批量）——需求的信号来自用户，不是猜测

## Status Quo

用户之前完全不管理库存——需要什么现买。遇到 HomeStock 后开始记录，但手动录入的摩擦让他们难以坚持。

当前流程：购物回家 → 打开飞书 → @机器人 → 逐条输入物品名称和数量

这个流程的问题：从「回家」到「录完」需要太多步骤和注意力。

## Target User & Narrowest Wedge

**目标用户**：家庭采购决策者（个人或家庭），已经使用飞书/微信作为日常沟通工具，有重复购买和食物过期的痛点。

**最窄的收费切入点**：自动购物清单生成——根据当前库存状态和消耗速度，告诉用户「该买什么了」。这个功能把「记录」和「购买」连起来了，用户能直接看到记录库存的价值。

## Constraints

- 现有 Go 后端 + React 前端的架构不变
- 飞书 bot 继续保持为主要输入入口
- 不引入需要大量运维成本的基础设施
- 渐进实施，每次改动后可运行

## Premises

1. **输入摩擦是当前最大瓶颈**——语音/图片/批量录入比增加更多库存管理功能更重要
2. **购物清单同步是最自然的付费切入点**——它在「记录」和「购买」之间搭了桥
3. **飞书是主要输入入口（语音/图片/文本），但输出/通知应通过多通道分发**——微信、企业微信、Telegram 等
4. **长期方向是自动捕获购买行为**（订单导入、小票识别），但短期内先降低主动录入门槛

## Cross-Model Perspective

独立顾问的冷读分析（Claude 子代理，未参与对话）：

**Steelman：** HomeStock 的最强形态不是库存管理工具，而是一个跨渠道的被动消费追踪网络。它自动捕获用户的每一笔购买行为，学习消耗节奏，在用户意识到需要之前就推送到购物清单上。

**关键洞察：** "用户永远不会有动力去主动记录库存。" 任何需要用户主动操作的录入方式都是死路。正确的方向是让录入自动发生——从淘宝/京东的购买记录导入，从小票拍照自动解析。

**挑战前提：** P3 可能反了——输入应该多渠道化（淘宝、小票、微信支付），输出反而应该集中在一个地方（微信）。

**创始人反驳**（有价值的分歧）：输出渠道就是与用户沟通的桥梁，分散输出和多渠道输入不矛盾。输入要广，输出也要广。

**48 小时原型提议：** 做一个"拍小票自动入库"的微信小程序——拍照 → 视觉模型 OCR → 自动提取物品 → 入库。不做用户系统、不做过期提醒、不做购物清单。

**采纳说明：** 拍小票自动入库的核心思路被采纳为近期输入升级的关键部分。

## Approaches Considered

### Approach A: 输入优先——降低录入门槛

仅升级 Feishu bot 的输入能力：语音输入、小票拍照识别、批量录入改进。输出渠道保持飞书不变。

- 工作量：H（语音 + OCR + NLP 三个独立模块） | 风险：低
- 优点：聚焦、快速交付、直接解决最痛的痛点
- 缺点：用户仍在单一渠道内，变现路径不明确

### Approach B: 功能变现——先做购物清单

优先开发自动购物清单生成作为付费功能，输入做基础改进。先验证付费意愿。

- 工作量：M | 风险：中（支付意愿不确定，且库存不准 → 清单不准的依赖链）
- 优点：验证商业模式、收入驱动
- 缺点：输入摩擦没解决前，购物清单的数据质量会受影响

### Approach C: 双管齐下——输入升级 + 输出扩展

同时做多模态输入（语音、拍照、批量）和多渠道输出（微信、Telegram），把体验做完整升级。

- 工作量：H-XL（8-12 周分 4 阶段实施） | 风险：中高
- 优点：一步到位解决核心问题、用户体验完整、长期架构正确
- 缺点：实施周期长，需要严谨分阶段执行，支付集成和微信渠道存在不确定风险

## Recommended Approach

选择 **Approach C（双管齐下）**，但分四阶段渐进实施，保持每个阶段独立可交付。总工作量 H-XL（8-12 周），但每阶段 2-3 周可交付增量价值。

## 渠道策略：输入即输出

**核心原则：用户的输入渠道 = 默认输出渠道。** 在飞书录入的用户，通知直接回到飞书。多通道输出的价值在于让**不在飞书的用户**也能用 HomeStock，而不是把每个用户的所有通知都推到所有渠道。

**去重规则：** 同一用户绑定多个渠道时，通知默认只发到用户的「主要渠道」（即其输入渠道）。用户可手动配置接收通知的渠道列表。

| 渠道 | 输入能力 | 输出能力 | 面向用户 | 阶段 |
|------|---------|---------|---------|------|
| 飞书 | 文本 / 语音 / 图片 | 通知推送 | 现有飞书用户 | Phase 1 |
| Telegram | 文本（Phase 4） | 通知推送 | 海外/Telegram用户 | Phase 2 |
| 微信 | 暂不支持 | 通知推送（探索性） | 国内非飞书用户 | Phase 2（探索） |
| 企业微信 | 文本（Phase 4） | 通知推送 | 企业用户 | Phase 2（探索） |

**场景示例：**
- 用户 A 通过飞书 bot 录入库存 → 过期提醒、购物清单都通过飞书 bot 发送 → 不推微信
- 用户 B 通过 Telegram bot 录入库存 → 通知通过 Telegram 发送 → 不推飞书
- 用户 C 绑定飞书+微信 → 飞书是主要渠道，微信为备用（仅当用户主动配置后才推送到微信）

## Execution Plan

### Phase 1a: 语音 + 批量输入升级（2 周）

**目标：** 让 Feishu bot 的文本/语音输入流畅可用。

1. **语音输入**：用户发语音消息 → 飞书语音转文字 → LLM 解析库存操作 → 自动入库
   - 利用飞书自带的语音转文字能力，无需额外 ASR 服务
   - LLM 解析层增强：从转写的文本中识别库存操作语义
2. **批量/多段输入改进**：优化自然语言解析，支持一次性输入"买了 5 斤苹果、2 箱牛奶、一袋大米"这样的多物品表达
3. **输入确认机制**（新增）：
   - 解析结果以结构化消息返回："识别到：苹果x5, 牛奶x2, 大米x1。确认入库请回 Y，修改请回 '改牛奶x3'"
   - 置信度低于阈值的结果标记为待确认
   - 提供"撤回最后一次入库"命令

### Phase 1b: 图片/小票识别（2-3 周，依赖 Assignment 结果）

**目标：** 用户拍照就能入库，不再需要打字。

1. **小票/物品拍照识别**：用户发照片 → 后端处理 → LLM 视觉模型识别物品 → 结构化入库
2. **确认修正闭环**：同 Phase 1a 的确认机制
3. **成本控制**：
   - 先用传统 OCR（如 PaddleOCR）提取文本，再用 LLM 做语义解析（降成本方案）
   - 或直接走 LLM 视觉 —— 取决于 Assignment 中的精度测试和 token 消耗评估
   - 设置每日/每用户调用限额

**乐观估算：2 周 | 悲观估算：3 周**（取决于 OCR 精度调优和模型选型）

### Phase 2: 输出多通道扩展（2-3 周）

**目标：** 用户在 Telegram 也能使用 HomeStock，探索微信可行性。

**原则：** 输出通知默认可通过飞书发送。多通道是指用户可以通过多种渠道使用 HomeStock（输入 + 输出），而不是将通知推送到所有渠道。

1. **Telegram 渠道（优先实现）**
   - 风险低、开发成本低、无封号风险
   - 支持：过期提醒、库存低量提醒、购物清单推送
   - 用户在 Telegram 绑定后，飞书和 Telegram 均可接收通知（默认发飞书，可配置）
2. **微信渠道（探索性）**
   - 风险：个人微信 bot 有封号风险；服务号模板消息逐步关闭
   - 方案待定：企业微信（需要资质）vs 小程序订阅通知
   - 如无法在合理风险内实现，标记为 "待调研" 并先推 Telegram
3. **通道抽象层完善**：
   - `pkg/channel/` 的接口需要明确定义：
   ```go
   type Channel interface {
       Send(userID string, msg *OutboundMessage) error
       Name() string
   }
   type OutboundMessage struct {
       Title    string
       Body     string
       Priority int    // 0=low, 1=normal, 2=urgent
   }
   ```

### Phase 3: 购物清单（MVP）+ 变现（4-5 周）

**目标：** 推出第一个付费功能。

**Phase 3a — 购物清单生成（2 周）**
1. **基于阈值的购物清单**：列出库存低于用户设定阈值的物品
   - 用户可为每个物品设置"低于 X 时提醒补充"
   - 清单输出为可读的结构化格式：物品名 + 建议数量
   - 可推送到所有已绑定的输出渠道
2. **冷启动策略**：
   - 新用户提供预设模板（"三口之家常备物品清单"）一键导入
   - 首次使用时引导用户设置关键物品的阈值
   - 数据不足时纯阈值模式，不依赖 ML 预测

**Phase 3b — 支付系统集成（2-3 周，可与 3a 并行）**
1. 支付渠道选型（待定：Stripe / 微信支付 / 支付宝）
2. 用户订阅管理系统
3. 付费功能解锁逻辑
4. **注意**：微信支付商户审核通常 1-2 周，需提前申请

### Phase 4: 长期演进（未来）

1. **淘宝/京东/拼多多订单导入**：通过电商开放平台 API 或浏览器插件
2. **消耗速度学习**：基于历史数据预测何时需要补充（ML 模型，非阈值）
3. **多通道输入扩展**：Telegram/企业微信也支持文本输入
4. **家庭共享**：多人协作维护库存
5. **微信/支付宝支付记录关联**：从支付数据推断购买物品

## 各阶段对用户的价值

| 阶段 | 用户得到什么 | 对产品的意义 |
|------|-------------|-------------|
| Phase 1a | 发语音就能入库，批量输入一次搞定 | 降低输入摩擦，提升留存 |
| Phase 1b | 拍小票照片就能自动入库 | 极大降低输入成本，改变使用习惯 |
| Phase 2 | 在 Telegram 也能使用 HomeStock（输入+输出） | 扩大用户覆盖范围，提升活跃 |
| Phase 3a | 自动知道该买什么了 | 第一个付费功能，验证商业模式 |
| Phase 3b | — | 支付基础设施，持续变现 |
| Phase 4 | 不用再录入任何东西 | 长期壁垒，从工具变成习惯 |

## Cost Analysis (LLM 视觉调用)

Phase 1b 的图片/小票识别走 LLM 视觉模型会产生持续 API 成本：

**估算基准：**
- 假设：用户每周购物 2 次，每次拍 1-2 张照片
- 每张图片消耗：2000-5000 tokens（取决于分辨率和压缩）
- DeepSeek Vision 价格：约 ¥1-2 / 百万 tokens
- 100 活跃用户：每月约 ¥30-80
- 1000 活跃用户：每月约 ¥300-800

**降成本策略：**
1. 先用传统 OCR（如 PaddleOCR）提取文本 → LLM 只做语义解析，token 消耗降 90%+
2. 用户端压缩图片再上传
3. 设置每日/每用户调用限额
4. Assignment 阶段实测 token 消耗，获得精确数据

## Distribution Plan

- Phase 1: 现有 Feishu bot 直接升级，用户无感
- Phase 2: 新增渠道配置入口，Settings 页面绑定
- Phase 3: 付费功能通过订阅制实现（支付宝/微信支付）
- Phase 4: 电商导入需要单独的浏览器插件或开放平台对接

## Open Questions

- 语音识别：走飞书自带的 ASR 还是直接传语音给 LLM？
- 小票 OCR：DeepSeek 视觉的中文小票识别精度如何？需要先测试（见 Assignment）
- 微信通知：走哪个路径？企业微信需要资质，个人 bot 有封号风险。备选：Telegram 先上，微信后续
- 支付渠道：Stripe（海外）还是微信支付/支付宝（国内）？取决于用户群体分布
- 通道抽象层：各 channel 是否需要保证送达/支持重试？模板渲染在抽象层统一做还是在各 channel 各自做？

## Success Criteria

1. Phase 1a: 用户录入一条库存的平均交互步骤减少 50%+（语音+批量 vs 逐条打字）
2. Phase 1b: 小票 OCR 精度 ≥80%（以首次识别无需人工修正为基准），且单张图片 API 成本 <¥0.05
3. Phase 2: 至少新增 1 个输出渠道（Telegram 优先）上线可用
4. Phase 3a: 购物清单功能上线，活跃用户中 30%+ 周均使用
5. Phase 3b: 付费转化率 >5% 活跃用户
6. 整体: 用户周留存率提升 20%+

## The Assignment

在接下来一周做一个最小实验：拍一张超市小票的照片发给飞书 bot，看 DeepSeek（已对接）的视觉能力能否正确识别出物品名称和数量。如果能达到 80%+ 的准确率，整个 Phase 1 的方向就是可行的。如果不行，需要评估换视觉模型或用结构化拍照模板。

这是整个升级计划的基础——如果拍照入库这条路通了，输入摩擦就从「大问题」变成「可解决的问题」。
