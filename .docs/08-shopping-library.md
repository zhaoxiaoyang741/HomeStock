# 08 - 家庭采购商品库方案

## 背景与目标

当前系统已经具备家庭库存管理能力，但购物列表仍偏向手工录入。为了更好支持家庭日常采购，后续可以在购物列表之外新增一层“商品库”，用于承接来自不同平台或渠道的候选商品，再由用户把商品加入自己的购物列表。

这个方案的核心目标不是直接做跨平台统一下单，而是先建立一套可扩展、可持续、可复用的数据接入模型：

- 面向家庭用户，帮助其从多个来源快速挑选常买商品。
- 将外部来源与内部购物列表解耦，避免系统核心能力被某一个平台绑定。
- 为后续扩展山姆、沃尔玛、本地超市、集市等来源预留统一插件接口。
- 明确区分真实官方数据、平台热度数据、系统推荐结果，避免把不同含义的数据混为“销量”。

本方案只讨论产品合理性、架构逻辑、数据来源边界和实现路径，不包含代码实现。

---

## 核心概念定义

### 购物列表

家庭自己的采购任务列表，是系统主数据的一部分。它表达的是“这次要买什么、买多少、优先级如何、是否已完成”，而不是“平台当前给了什么商品”。

购物列表必须独立于外部平台存在。即使某个来源后续失效、链接下线、价格变化，已加入的购物列表项仍应保留。

### 商品库

外部来源商品集合。它的职责是提供候选商品、热度信息、价格信息、来源链接、规格信息等，供用户选择后加入购物列表。

商品库不是购物列表本身，也不是库存本身。它更接近“选品池”或“候选目录”。

### 来源插件

接入某个平台、某一类商品源、某一种合作数据形式的统一封装。插件负责把外部来源的商品、热度、价格、链接、门店等字段转换成系统内部统一格式。

来源插件是后续横向扩展的核心抽象。以后无论接入山姆、沃尔玛、淘宝、菜市场导表，原则上都只新增插件，不改购物列表核心模型。

### 商品快照

用户把某个来源商品加入购物列表时保存的一份副本。快照应至少保留用户当时看到的标题、规格、价格、来源、外部链接、图片和来源时间。

商品快照的作用是防止外部商品变化后，购物列表丢失上下文。

## 整体架构与职责边界

建议把能力拆成四层：

1. `SourcePlugin`
2. `SourceLibrary`
3. `SourceItem`
4. `ShoppingListItem`

### 1. SourcePlugin

`SourcePlugin` 表示一个可扩展的来源接入器，例如：

- 山姆中国插件
- 沃尔玛中国插件
- 淘宝联盟插件
- 本地市场手工库插件

它解决的问题是：不同平台数据结构不同、权限不同、字段不同、刷新方式不同，系统需要一个统一的适配层。

它与其他对象的关系：

- 一个 `SourcePlugin` 可以管理多个 `SourceLibrary`
- 插件负责产出统一格式的 `SourceItem`
- `ShoppingListItem` 不直接依赖插件在线存在，但会记录来源插件信息

建议保留的关键字段：

- `plugin_id`
- `plugin_name`
- `plugin_type`
- `region`
- `auth_mode`
- `capabilities`
- `data_trust_level`
- `refresh_policy`
- `status`

### 2. SourceLibrary

`SourceLibrary` 表示插件下的某个具体商品库或商品域。它解决的问题是：同一个插件下可能存在多个不同逻辑的商品集合。

例如：

- 山姆中国 / 会员店商品库
- 沃尔玛中国 / 网上超市商品库
- 淘宝联盟 / 日用百货物料库
- 本地市场 / 蔬菜手工库

它与其他对象的关系：

- 一个 `SourceLibrary` 属于一个 `SourcePlugin`
- 一个 `SourceLibrary` 包含多个 `SourceItem`
- 用户从 `SourceLibrary` 选择 `SourceItem` 加入 `ShoppingListItem`

建议保留的关键字段：

- `library_id`
- `plugin_id`
- `library_name`
- `library_scope`
- `category_scope`
- `geo_scope`
- `currency`
- `update_frequency`
- `access_constraints`

### 3. SourceItem

`SourceItem` 表示来源商品的统一结构。它解决的问题是：不同平台的商品字段不一致，但前端展示和购物列表加入动作需要统一数据模型。

它与其他对象的关系：

- 一个 `SourceItem` 来自一个 `SourceLibrary`
- 一个 `SourceItem` 可以被多次加入多个 `ShoppingListItem`

建议保留的关键字段：

- `source_item_id`
- `external_item_id`
- `plugin_id`
- `library_id`
- `title`
- `brand`
- `spec`
- `unit`
- `price`
- `price_label`
- `image_url`
- `product_url`
- `store_name`
- `geo_info`
- `availability`
- `ranking_type`
- `ranking_value`
- `sales_label`
- `source_timestamp`
- `raw_source_ref`

### 4. ShoppingListItem

`ShoppingListItem` 表示家庭购物任务中的一项。它解决的问题是：把家庭采购目标和外部商品候选区分开，同时保留来源上下文。

它与其他对象的关系：

- `ShoppingListItem` 可以由手工创建，也可以由 `SourceItem` 派生
- 购物列表项保存来源快照，但不依赖来源在线可用

建议保留的关键字段：

- `shopping_list_item_id`
- `tenant_id`
- `title`
- `planned_quantity`
- `planned_unit`
- `priority`
- `status`
- `preferred_source_plugin_id`
- `preferred_source_library_id`
- `source_snapshot`
- `notes`
- `created_at`
- `updated_at`

## 商品库插件化扩展模型

插件设计不要按平台名字硬编码，而应按“能力边界”抽象。这样未来接入不同来源时，系统核心逻辑无需重写。

建议约定以下插件能力：

### 必选能力

- `search_items`
  - 根据关键词、类目、品牌等检索来源商品
- `get_item_detail`
  - 获取某个来源商品的完整信息
- `build_purchase_link`
  - 生成可跳转的购买或查看链接

### 推荐能力

- `list_ranked_items`
  - 拉取榜单、热卖、精选、推荐池等排序结果
- `refresh_price`
  - 在需要时刷新价格或可售状态

### 未来可选能力

- `place_order`
  - 发起下单
- `sync_cart`
  - 与目标平台购物车同步
- `sync_order_status`
  - 查询订单状态

第一阶段建议只要求做到“选品、加入列表、跳转”，不要把统一下单作为落地前提。

## 购物列表与商品库的关系

这两个模块的关系建议固定为：

- 购物列表是家庭采购任务中心
- 商品库是外部候选商品来源
- 商品库服务于购物列表，不反向替代购物列表

推荐的用户路径：

1. 用户先有购物需求，例如“鸡蛋、牛奶、抽纸”
2. 系统可从多个商品库给出候选商品
3. 用户选择具体商品加入购物列表
4. 购物列表保留来源快照
5. 用户后续可跳转原平台查看或购买

这样设计有几个好处：

- 即使某个平台没有稳定接口，也不影响购物列表主流程
- 即使外部价格变化，购物列表仍保留用户选择记录
- 即使将来新增更多平台，也不需要改购物列表基础模型

---

## 热销、热度、推荐的定义与展示原则

“销量高”在这个场景里是一个高风险词，必须拆开定义。

### 1. 官方销量

只有当来源明确提供销量字段时，才能称为“官方销量”或“平台销量”。

例如某些联盟或开放平台会给出“近 30 天销量”“总销量”等字段，这类数据可以直接展示，但必须保留来源说明和时间说明。

### 2. 平台热度

当来源没有直接开放销量字段，但存在榜单、热卖标记、搜索排序、精选池、推荐位时，这类信息只能称为“平台热度”。

它能表达平台推荐强度，但不等于实际成交销量。

### 3. 系统推荐

系统可以结合家庭历史采购、库存缺口、使用频率、预算区间、偏好店铺等信息生成推荐结果。这类结果属于“系统推荐”，不是平台原始数据。

### 展示原则

- 不把三类信息混写成统一的“销量”
- 每个来源明确标注数据类型和时间
- 跨平台不直接比较原始销量值
- 跨平台排序只比较标准化热度分位和家庭匹配度

否则会出现明显误导：

- 山姆的“热卖”不一定能与淘宝的“30 天销量”直接对比
- 本地市场手工库可能根本没有销量字段
- 同一商品在不同平台上的包装规格不同，原始销量没有直接可比性

## 真实数据来源与可信度分级

从长期可维护性角度，建议把来源分成三类。

### A. 标准化开放来源

定义：有明确官方开放平台、联盟平台或开发者文档，字段结构较稳定，可持续接入。

特点：

- 结构化字段较完整
- 权限和调用边界较清晰
- 最适合做标准插件

典型例子：

- 淘宝联盟商品物料接口
- 未来若有京东联盟、多多进宝等官方开放能力，也可归入这一类

可信度结论：

- 这是第一阶段最适合落地的来源类型

### B. 官方消费渠道来源

定义：来源属于官方消费者渠道，例如官网、官方 App、官方小程序、官方到家入口，但未必对普通开发者开放结构化商品 API 或销量 API。

特点：

- 来源本身是真实官方渠道
- 适合承接展示、跳转、人工运营库
- 不代表天然具备可持续 API

典型例子：

- 山姆中国 App
- 沃尔玛中国网上超市
- 京东到家中的官方商超入口

可信度结论：

- 适合做“可展示、可跳转、可半自动维护”的来源
- 不适合直接假设为“可长期程序化抓取的标准来源”

### C. 半结构化来源

定义：没有标准官方商品 API，只能通过商家合作导表、POS 或 ERP 导出、人工维护、半自动录入等方式接入。

特点：

- 最灵活
- 数据完整性和实时性最弱
- 适合本地菜市场、社区超市、熟人商家

可信度结论：

- 可作为补充来源
- 不应承担统一热销榜和统一比价主职责

### 建议的可信度标签

为了避免后续产品含义混乱，建议对每个来源记录一个可信度等级：

- `official_structured`
- `official_channel`
- `partner_feed`
- `manual_curated`
- `inferred`

其中 `inferred` 只能用于推断型信息，不能当作官方销量展示。

## 各类来源的可行性评估

### 淘宝联盟类来源

可行性：高。

原因：

- 存在明确官方文档和结构化接口
- 可获取商品基础信息、价格、推广链接
- 适合做标准插件

截至 2026-04-09，本方案确认的公开官方参考之一是淘宝客物料搜索接口：

- `taobao.tbk.dg.material.optional`
- 官方文档链接：<https://open.alitrip.com/doc2/apiDetail.htm?apiId=35896>

适合作为第一批标准化来源的原因：

- 字段结构清晰
- 接入逻辑标准化
- 可以支持“搜索商品、展示信息、跳转原平台”

注意点：

- 联盟数据的业务目标偏导购和推广，不等于全平台完整商品数据
- 字段是否包含销量、销量时间范围、排序能力，必须按官方文档说明展示，不应自行扩展解释

### 山姆中国 / 沃尔玛中国

可行性：中。

原因：

- 官方消费渠道真实存在，用户认知强，商品价值高
- 但普通开发者面向消费者侧的公开结构化商品 API 较难确认

截至 2026-04-09，本方案确认到的官方参考包括：

- 沃尔玛中国零售链系统：<https://www.walmart.cn/retail/>
- 山姆业务介绍：<https://www.walmart.cn/aboutus-4/>
- 沃尔玛中国全渠道说明：<https://www.walmart.cn/aboutus-6/>
- 山姆供应商申请入口：<https://www.walmart.cn/apply-sam/>

这些信息说明：

- 沃尔玛和山姆存在成熟商品与销售数据体系
- 面向供应商存在更深入的数据协同能力
- 面向消费者的官方渠道真实存在

但需要明确：

- 零售链更偏供应商体系，不适合直接假设为普通家庭应用可接入的数据源
- 截至 2026-04-09，本次检索中未发现面向普通开发者公开开放的“山姆中国商品/销量 API”官方文档
- 这是一条基于公开检索结果的推断，不代表官方明确否认

因此山姆中国、沃尔玛中国更适合在第一阶段作为：

- 官方渠道展示库
- 半自动维护库
- 未来有合作条件后升级为正式插件接入

### 本地超市 / 集市

可行性：中到高，取决于运营方式。

原因：

- 业务价值很高，符合家庭采购真实场景
- 但标准化程度最低

建议做法：

- 先做手工维护库或导表库
- 再做合作商家 feed 接入
- 最后才考虑实时接口

不建议的假设：

- 不要默认本地市场天然存在稳定开放 API
- 不要把人工维护数据伪装成平台实时销量数据

### 沃尔玛国际开放能力

可行性：作为架构参考，高。作为中国家庭场景首个数据源，低。

官方参考：

- Walmart Marketplace APIs introduction:
  <https://developer.walmart.com/us-marketplace/docs/introduction-to-marketplace-apis>
- Walmart Item Search API:
  <https://developer.walmart.com/us-marketplace/reference/getsearchresult>

价值：

- 证明“商品库插件化接入”这条架构路线本身是合理的
- 可作为未来国际化或合作化场景的参考

限制：

- 面向美国市场和卖家生态
- 不适合作为中国家庭采购场景的首个真实数据源

## 分阶段落地路径

### Phase 1 - 建立购物列表与商品库分层

目标：

- 先完成核心模型分离
- 明确 `ShoppingListItem` 和 `SourceItem` 的关系
- 支持来源快照保存

能力范围：

- 手工购物列表
- 简单来源商品展示
- 从来源加入购物列表

### Phase 2 - 接入第一批标准化来源

优先建议：

- 先接“标准化开放来源”
- 例如淘宝联盟类来源

能力范围：

- 搜索商品
- 获取详情
- 构建跳转链接
- 基础热度展示

### Phase 3 - 接入官方渠道展示库

优先建议：

- 增加山姆中国、沃尔玛中国等官方消费渠道来源
- 先以展示、跳转、人工运营补足为主

能力范围：

- 展示商品目录
- 展示门店或渠道信息
- 保存来源快照

### Phase 4 - 接入半结构化本地来源

优先建议：

- 支持本地超市、菜市场导表和手工库

能力范围：

- 人工导入
- 商品映射
- 简单推荐

### Phase 5 - 评估平台下单能力

只有在以下前提满足时才建议进入：

- 某些来源已有明确授权能力
- 履约、订单、售后边界可控
- 合规和风控要求已明确

否则统一下单会显著抬高复杂度，不适合作为早期前提。

## 风险与边界

### 1. 数据真实性风险

最常见的问题不是“拿不到商品”，而是“拿到的热度含义不一致”。因此所有来源都必须标注：

- 数据来源
- 字段含义
- 时间范围
- 是否官方结构化来源

### 2. 合规与授权风险

如果某来源没有明确开放能力，不应把页面抓取默认视为长期方案。即使技术上能实现，也不代表适合做正式系统能力。

### 3. 跨平台可比性风险

不同平台的销量口径、SKU 规格、活动方式、门店覆盖范围都不同，不能把原始销量直接做统一排序。

### 4. 来源失效风险

外部来源字段、链接、权限可能变化，因此购物列表必须保存来源快照，系统核心流程不能依赖外部源永远在线。

### 5. 运营成本风险

本地市场和半结构化来源更像运营问题，不只是技术问题。如果后续重点覆盖这类来源，需要预留人工维护流程。

---

## 复核清单

后续详细确认时，优先复核以下问题是否已经回答清楚：

- 山姆、沃尔玛、淘宝、本地市场是否都能放进同一插件模型
- “销量高”是否已经拆分成官方销量、平台热度、系统推荐三种概念
- 购物列表是否独立于外部平台存在
- 新增一个来源时，是否无需重写购物列表核心逻辑
- 文档中哪些属于官方真实来源，哪些属于推断或合作前提，是否已经标注清楚

---

## 结论

从产品合理性和架构可扩展性看，“家庭购物列表 + 多来源商品库”是可行方向。

最合理的实现逻辑不是直接做跨平台统一下单，而是先把系统主数据固定为家庭购物列表，再把外部平台都作为“来源插件”接入。这样既能支持未来横向扩展，也能把数据真实性、合规性和来源失效风险控制在可接受范围内。

第一阶段最适合落地的路径是：

- 先完成购物列表与商品库的模型分离
- 再优先接入标准化开放来源
- 同时为山姆、沃尔玛、本地市场预留统一插件框架
- 最后视授权条件评估是否进入下单能力

这条路径兼顾了可实施性、扩展性和后续运营现实。
